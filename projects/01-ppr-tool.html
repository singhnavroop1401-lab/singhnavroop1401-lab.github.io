The requirement

The Product–Process–Resource paradigm describes three things at once: what is produced, how it is produced, and which resources produce it. Because the three perspectives share one structure but are read by different engineering disciplines, the requirement is specific — expose multiple engineering views over one common graph without duplicating the data. Two copies of the model that drift apart would defeat the purpose.

Around that core, the brief asked for a full workflow: a self-designed input format with import logic, an internal graph representation, create/read/update/delete operations that cannot break PPR conformance, view-specific analysis, graph algorithms that check the model against engineering requirements, and public deployment. The domain model is the group's Lego Race Car assembly line — small enough to reason about, structurally non-trivial.

Approach

Everything hangs off a single networkx.DiGraph held in Streamlit's session state. Products, processes and resources are nodes carrying a mandatory type attribute plus any number of view-specific attributes; edges carry a readable relation label such as performs, produces or inspects. Because every module reads that one graph directly, an edit made in the CRUD tab is immediately visible in every view and every algorithm — there is no cached projection that can go stale.

The layering is deliberate: parsing, graph mechanics and presentation are separate, and only the presentation layer imports Streamlit. The graph layer is plain Python and can be exercised without a UI.

  • Input format. A unified node/edge list, chosen because it maps directly onto NetworkX and expresses the same structure in JSON (canonical), XML and Excel with no information loss. One entry point detects the extension, dispatches to the right parser, and surfaces parse failures as readable errors instead of a stack trace.
  • Conformance at the boundary. Only two edge directions are meaningful — Resource → Process ("performs") and Process → Product ("produces"). The whitelist is enforced inside the edge-creation function, so a bad edge is rejected before the graph is touched, and the same check runs over bulk imports. The error names the violation: Cannot connect Resource → Product.
  • Engineering view. Projects cost, mass, assembly time and Overall Equipment Effectiveness into the node labels, and aggregates them into system-level KPIs.
  • Reliability view. Projects a different attribute set — MTBF, MTTR, failure probability, maintenance interval — and overlays failure-dependency edges as dashed arrows on top of the PPR structure, so a propagation path is visible rather than inferred.
  • One renderer, not one per view. Both the static Graphviz renderer and the interactive PyVis renderer take the same three arguments: which nodes the current view highlights, whether to draw the view alone or the whole graph with the rest dimmed, and any extra overlay edges. That parameterisation is what lets a single rendering module serve every view, every traceability panel and the algorithms tab without duplicated drawing code.

The reliability view, specifically

This is the part I owned, so it is the part worth going into. A reliability edge is not a PPR edge: PPR structure says "this process produces that product", while a failure dependency says "if this node fails, that node's function is compromised". They are different relations over the same node set, which is exactly why the view overlays them instead of adding them to the graph as ordinary edges — putting them in the structure would corrupt the conformance rules that make the model checkable.

On the sample assembly line the overlay carries three dependencies: an axle failure takes out wheel mounting, a chassis failure detaches the body block, and a spoiler detachment stresses the chassis. The view then ranks every node by MTBF and MTTR and flags anything with a failure probability above 4% — on the sample model the wheels, the spoiler, the axle and one human resource, which is the useful part: the operator ranks alongside the hardware, because the model does not privilege machines over people.

Reliability attributes are held in a separate table rather than in the structural model, so a real data set can be swapped in without touching the graph. That was the right call for separation and the wrong call for provenance — see below.

The same overlay drives the failure-propagation algorithm, so the view and the check cannot disagree about what depends on what. The four checks are:

CheckQuestion it answersGraph primitive
PPR coverageDoes every product have an assembling process, and every process an assigned resource?predecessors()
View-specific dependenciesIf this node fails, what else is affected?descendants()
Structural similarityWhich elements share a signature of type, predecessor types and successor types?combinations()
Disconnected segmentsIs any part of the line detached from the rest of the assembly?weakly_connected_components()

Result

A deployed tool that loads a model in one click, renders it two ways, projects it through two engineering views, edits it in place with conformance enforced, and validates it against four requirement checks — all against a single graph, with every change propagating immediately. Delete the resource edge feeding a process and the coverage check names that process as a violation on the next run; delete the edges around a jig and the segment check splits the graph and lists both components. The demonstration path is the audit trail.

Two design choices carried the most weight, and both are about keeping the user out of trouble rather than about features. Typed widgets per node type mean a malformed value cannot reach the model — assembly time is a number, OEE is a slider bounded to 0–1, so "ninety percent" as a string is not expressible. And the pre-filled editor loads a node's current attributes before the user types, so every edit is an informed modification instead of a blind overwrite.

What I'd do differently

  • Reliability data belongs in the model file. Holding MTBF, MTTR and failure probabilities in a module-level table made the demo trivial and the provenance wrong: the numbers cannot be traced to a source, versioned with the model, or supplied by whoever actually owns the maintenance history. Lifting them into the input format is the single change that would make the reliability view usable on a real line rather than a sample one.
  • The failure-dependency list should be one constant, not two. The view and the propagation algorithm each held their own copy. They were kept in step by name and by being driven from the same list, but that is a convention, not a guarantee — a shared constants module removes the class of bug entirely.
  • No export. The tool imports three formats and writes none. The serialisation helper already exists, so a download button is a small change with a disproportionate effect: without it, every edit made in the app dies with the session.
  • The graph layer is testable and untested. Keeping Streamlit out of the graph modules was worth doing precisely because it makes them unit-testable — and then no tests were written. Conformance rejection, propagation reachability and the similarity signature are all pure functions with obvious cases.
